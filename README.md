# Гармония (Harmony)

Спокойная социальная сеть: публикации, комментарии, личные чаты и разговор в
приватном ключе. Построена как продакшн-сервис — с аутентификацией, модерацией,
защитой от спама, правами пользователей по GDPR, документацией API и
воспроизводимым развёртыванием.

```
Локальный запуск:  make install && make dev
Полный стек:      make up
```

## Быстрый старт

### Требования

| Компонент | Версия | Обязателен |
|---|---|---|
| Python | 3.11+ | да |
| PostgreSQL | 14+ | да |
| Redis | 6+ | нет, но настоятельно рекомендуется |
| Docker + Compose | v2 | для полного стека |
| Node.js | — | нет: фронтенд не требует сборки |

### Локально, без Docker

```bash
git clone https://github.com/your-org/harmony.git
cd harmony

make install                     # venv + зависимости
cp .env.example .env             # затем заполните SECRET_KEY и DATABASE_URL

make migrate                     # применить миграции
make seed                        # демонстрационные данные (необязательно)
make dev                         # http://localhost:8000
```

Redis необязателен: без него отключаются кэш и распределённый rate limit,
приложение работает на локальных реализациях и предупреждает в логах.

### Docker Compose

```bash
cp .env.example .env
make secret                      # сгенерировать SECRET_KEY и JWT_SECRET_KEY
# впишите их в .env, задайте DB_PASSWORD и SITE_URL

make up                          # db, redis, api, worker, beat, nginx
make migrate-docker              # применить миграции
make seed-docker                 # демонстрационные данные
```

Откройте <http://localhost>.

### Первый администратор

```bash
make create-admin                # интерактивно спрашивает почту и пароль
```

Либо задайте `ADMIN_EMAIL` и `ADMIN_PASSWORD` (минимум 12 символов) до
первого запуска — аккаунт создастся автоматически, и только если
администраторов ещё нет.

```
       │  (static)    │          │  (gunicorn) │
       └──────────────┘          └──────┬──────┘
                                         │
              ┌──────────────────────────┼──────────────────────────┐
              │                          │                          │
       ┌──────▼──────┐           ┌───────▼──────┐           ┌───────▼──────┐
       │ PostgreSQL  │           │    Redis     │           │   Celery     │
       │  (данные)   │           │ кэш/лимиты/  │           │  worker × N  │
       └─────────────┘           │ очередь WS   │           └───────┬──────┘
                                 └──────────────┘                   │
                                                           ┌────────▼───────┐
                                                           │  beat (×1)     │
                                                           │  таймеры, GDPR │
                                                           └────────────────┘
```

### Слои бэкенда

| Слой | Путь | Ответственность |
|---|---|---|
| `api/` | `app/api/` | HTTP: маршруты, коды ответов, контракт |
| `services/` | `app/services/` | Бизнес-логика; не знает про `request` |
| `security/` | `app/security/` | валидация, XSS, фильтры, rate limit, CSRF |
| `models/` | `app/models/` | SQLAlchemy 2.0, индексы, сериализация |
| `realtime/` | `app/realtime/` | WebSocket-события и комнаты |
| `tasks/` | `app/tasks/` | Фоновые задачи и расписание |
| `utils/` | `app/utils/` | Ответы, пагинация, логи, крипто, метрики |

Правило: `api` может вызывать `services`, `services` — `models` и `security`.
Обратных зависимостей нет. Поэтому вся бизнес-логика тестируется без HTTP-клиента.

### Фронтенд

ES-модули без сборщика и без зависимостей. Роутер на History API, наблюдаемое
хранилище состояния, компоненты возвращают DOM-узлы.

```
frontend/
├── index.html
├── css/     base (токены) · components · layout · pages
├── js/
│   ├── core/     api · store · router · dom · icons · format · toast
│   ├── components/  ui · shell · composer · report
│   ├── pages/    feed · post · profile · search · chat
│   │             settings · admin · notifications · auth · legal
│   └── main.js
└── assets/  logo.svg · mark.svg · favicon.svg · иконки PNG
```

## Дизайн-система

Спокойный минимализм: тёплая нейтральная база, один приглушённый
сине-серый акцент, много воздуха, тонкие разделители вместо ярких пятен.

### Палитра

| Токен | Значение | Назначение |
|---|---|---|
| `--sand-50` | `#faf9f7` | фон страницы |
| `--sand-100…400` | `#f5f3f0`…`#d2ccc2` | границы, приподнятые поверхности |
| `--stone-500…700` | `#a8a196`…`#6f6862` | приглушённый текст |
| `--ink-800…950` | `#4a4640`…`#1a1917` | основной текст |
| `--dusk-50…700` | `#f2f5f6`…`#3f515b` | акцент |
| `--avatar-*` | 8 оттенков | аватары, назначаются детерминированно |

Контраст текста к фону — не ниже WCAG AA (4.5:1). Акцент нигде не является
единственным носителем смысла: состояние всегда подкреплено формой или текстом.

### Типографика

Inter с системным запасным вариантом. Шкала 1.2: 12 → 33 px. Заголовки
сбалансированы через `text-wrap: balance`, основной текст — через `pretty`.

### Логотип

Две переплетающиеся плавные линии: расходятся от общей точки вверху, пересекаются
внизу и замыкаются в форму сердца-листа. Монохромная палитра — тёплый камень и
мягкий песок. Читается на 16 px, годится как favicon, app icon и марка.

Иконки генерируются из той же геометрии скриптом `tools/generate_icons.py`
(чистый Python, без зависимостей, побайтово воспроизводимо):

```bash
python tools/generate_icons.py
```

## Безопасность

### Аутентификация

| Механизм | Решение | Почему |
|---|---|---|
| Хранение паролей | bcrypt, 12 раундов | Отражено в тестах |
| Сессия | JWT в `HttpOnly`-cookie | XSS не может прочитать токен |
| Обновление | Ротация refresh-токена | Повтор отозванного токена отзывает все сессии |
| Отзыв | Строка сессии в БД | Выход на всех устройствах |
| Инвалидация | `ver` в claims | Смена статуса делает старые токены недействительными |
| Чувствительные действия | Step-up (`reauth_token`) | Удаление аккаунта требует пароль даже при живом токене |

> Длинные пароли предварительно хешируются SHA-256: bcrypt молча игнорирует
> байты после 72-го, и без этого шага суффикс перестал бы влиять на пароль.

### Защита от перечисления

`/auth/login`, `/auth/register`, `/auth/forgot-password`,
`/auth/resend-verification` не раскрывают существование аккаунта. Неизвестный
логин всё равно выполняет bcrypt-проверку (фиктивный хеш), чтобы время ответа
не выдавало разницу.

### CSRF

Двойная отправка: `harmony_csrf` (читаемая cookie) + заголовок
`X-CSRF-Token` на каждый изменяющий запрос. Корректные `Origin`/`Referer`
принимаются как эквивалент — иначе не работали бы мобильные клиенты.

### XSS

Контент хранится как **обычный текст**. API никогда не возвращает HTML, а
фронтенд пишет через `textContent`. Политика безопасности без `unsafe-inline`
для скриптов — самая эффективная защита в стеке. Очистка на входе — второй
слой, а не основной.

### Ограничение частоты

Скользящее окно на Redis (Lua-атомарно). Счётчик запросов хранится в
отсортированном множестве, что не даёт выиграть «2× лимита» на стыке окон —
в отличие от фиксированного окна.

### Anti-бот

nonce, у которого SHA-256 начинается с N нулевых бит. Считается в Web Worker,
без сторонних сервисов и без трекинга. Это контроль *стоимости* для
автоматизации, а не доказательство человечности. Cloudflare Turnstile и

Каждая задача одноразовая: она удаляется из хранилища при первой попытке
всегда; при входе она становится обязательной, как только идентичность
выглядит целью перебора паролей — свежие неудачные попытки, счётчик у порога
блокировки или живая блокировка аккаунта. Требовать её от каждого входа нельзя:
люди начинают отдавать ответы ботам.

### Заголовки

`CSP` без `unsafe-inline` для скриптов · `nosniff` · `DENY` ·
`Referrer-Policy` · `Permissions-Policy` · HSTS · `X-Permitted-Cross-Domain-Policies`.

### Аудит

Неизменяемый журнал действий модераторов и значимых событий. Хранит
идентификаторы и причины, но не содержимое сообщений. IP — только в виде
HMAC-хеша: это персональные данные, и в открытом виде они не хранятся.

## Модерация

### Два слоя

```
Локальный анализатор            Внешний классификатор (необязательно)
  PII, угрозы, язык ненависти ──▶  может только УСИЛИТЬ решение
  опасный контент, спам, XSS        локального слоя
        │                                    │
        └──────────────┬─────────────────────┘
                       ▼
              allow · review · block
```

Асимметрия намеренная: сбой, квота или неверная настройка внешнего API не
должны превращаться в обход модерации.

### Автоматические решения

- `block` → 451, контент не сохраняется
- `review` → 202, контент сохранён со статусом `under_review`
- `allow` → публикуется

### Эскалация по жалобам

Контент скрывается автоматически, когда его отметили **разные** люди
(порог настраивается). Ложное срабатывание стоит автору нескольких минут
ожидания; ложное отсутствие реакции на действительно вредный контент
необратимо.

### Санкции

Скрытие · предупреждение · приостановка (1 час — 12 месяцев) · блокировка ·
восстановление. Любая мера фиксируется в журнале, любая — обжалуема. Истечение
срока обрабатывается автоматически (`moderation.expire_actions`).

## Приватность и GDPR

| Статья | Механизм |
|---|---|
| 15, 20 | `GET /me/data` · `POST /me/data/export` (JSON, 7 дней) |
| 16 | Изменение профиля |
| 17 | `POST /me/deletion` с льготным периодом и отменой |
| 18 | `POST /me/data/restriction` |
| 21 | `POST /me/data/objection` · `/me/data/consent` |
| 30 | `GET /legal/processing-register` — реестр формируется из живой конфигурации |
| 5(1)(e) | Сроки хранения применяются таймерами |

### Что удаляется, а что нет

Удаляются: публикации, комментарии, реакции, личные сообщения, файлы, сессии,
токены, согласия, запросы.

**Сохраняются** записи о санкциях без связи с аккаунтом. Это требование
законодательства о модерации, а не удержание профиля, и это сказано
пользователю прямо в политике.

### Сроки

| Категория | Срок |
|---|---|
| Данные аккаунта | до удаления |
| События антиспама | 24 часа |
| Журнал доставки писем | 90 дней |
| Уведомления | 90 дней |
| Выгрузки данных | 7 дней |
| Агрегатные метрики | 30 дней |

Полный перечень cookie — `GET /api/v1/legal/cookies`. Сторонних и рекламных
cookie нет.

## Масштабирование

### Почему keyset, а не offset

Пагинация курсорами остаётся корректной, когда строки добавляются во время
прокрутки: `OFFSET` пропускает и дублирует элементы, курсор — нет. Индексы
составлены под точный запрос ленты.

### Денормализация счётчиков

`likes_count` и `comments_count` пересчитываются из строк в той же транзакции,
а не инкрементом: повторный запрос или гонка не расшатывают счётчик.

### Кэш

Только неизменяемые или чётко ограниченные данные. Ключи вида
`harmony:<tag>:<hash>` — по тегу можно сбросить целую категорию через `SCAN`,
не угадывая ключи. Любой сбой кэша деградирует в промах, а не в ошибку.

### Горизонтальное масштабирование

- `SOCKETIO_ASYNC_MODE=gevent` + `SOCKETIO_MESSAGE_QUEUE=redis://…` —
  сокет, открытый на одном поде, виден всем остальным
- комнаты `user:<id>` и `conversation:<id>` детерминированы
- `Celery beat` — **ровно один** экземпляр: два планировщика означают
  двойные письма и двойные удаления

```bash
BACKEND_REPLICAS=6 CELERY_CONCURRENCY=8 make up
```

## Наблюдаемость

### Метрики

`GET /metrics` (Prometheus). Метки ограничены шаблоном маршрута, а не сырым
путём: иначе кардинальность взорвалась бы перебором идентификаторов.

| Метрика | Смысл |
|---|---|
| `harmony_http_requests_total` | запросы по маршруту и статусу |
| `harmony_http_request_duration_seconds` | латентность |
| `harmony_db_query_duration_seconds` | время SQL-запросов |
| `harmony_rate_limit_hits_total` | срабатывания ограничений |
| `harmony_moderation_decisions_total` | решения модерации |
| `harmony_celery_tasks_total` | исход задач |
| `harmony_realtime_events_total` | события WebSocket |

### Проверки

- `/healthz` — процесс жив (не трогает БД)
- `/readyz` — PostgreSQL и Redis отвечают
- `/metrics` — метрики; nginx закрывает доступ извне

### Логи

Структурированный JSON, одна строка на событие, `request_id` связывает запись
с пользовательским сообщением об ошибке. Ключи с секретами маскируются на
уровне форматтера.

```bash
make observability    # Grafana на :3000, Prometheus на :9090
```

## API

Префикс: `/api/v1`. Интерактивная документация: `/api/docs`.
Исходник спецификации: `spec/openapi.yaml`.

```json
// успех
{ "ok": true, "data": { }, "meta": { "count": 15, "has_more": true, "next_cursor": "eyJ…" } }

// ошибка
{ "ok": false, "error": { "code": "not_found", "message": "Пост не найден.", "request_id": "…" } }
```

Ресурсы адресуются непрозрачным `public_id`, а не последовательным `id`:
перебор идентификаторов утекает объём и упрощает ошибки авторизации.

```bash
# пагинация
curl -s 'localhost:8000/api/v1/feed?limit=15' | jq .meta
curl -s 'localhost:8000/api/v1/feed?cursor=eyJ…' | jq '.data[].body'

# вход
curl -s -X POST localhost:8000/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"identifier":"mira","password":"…"}' -c cookies.txt

# публикация
curl -s -X POST localhost:8000/api/v1/posts \
  -H 'Content-Type: application/json' \
  -H "X-CSRF-Token: $(grep harmony_csrf cookies.txt | awk '{print $7}')" \
  -b cookies.txt -d '{"body":"Спокойное утро"}'
```

Коды ошибок: `validation_failed` (422), `unauthenticated` (401),
`email_not_verified` (403), `csrf_token_invalid` (403), `not_found` (404),
`rate_limited` (429), `content_blocked` (451),
`content_under_review` (202).

> `404` возвращается и для контента, который существует, но скрыт от
> запрашивающего: иначе настройки приватности протекали бы через API.

## Тестирование

```bash
make test            # весь набор
make test-fast       # до первого падения
make test-cov        # с отчётом о покрытии
make lint            # ruff
make check           # lint + тесты + согласованность спецификации и фронтенда
```

Отдельно, потому что это проверки согласованности артефактов, а не поведения:

```bash
make openapi-check   # openapi.json не устарел относительно openapi.yaml
make check-routes    # каждый маршрут описан, каждая операция существует
make check-frontend  # каждый импорт разрешается, каждый innerHTML пересмотрен
```

Тесты проверяют свойства, а не строки реализации:

- **нет перечисления** — сообщения для существующего и несуществующего аккаунта совпадают
- **CSRF работает** — запрос без токена отклоняется настоящим декоратором, а не отключённым
- **приватность соблюдается** — скрытый контент возвращает 404, а не 403
- **внешний модератор не может ослабить** — проверяется merge по возрастанию
- **санкция видна как санкция** — забаненный получает `403 account_banned`, а не «сессия завершена»
- **удаление аккаунта** стирает всё и оставляет аудит без привязки
- **удаление поста обратимо** — строка скрыта, но не уничтожена, и `restore` работает
- **повтор запроса безвреден** — лайк не снимается сам, step-up токен не тратится дважды
- **загрузка** отвергает файл, переименованный в `.png`

В CI набор идёт против настоящих PostgreSQL и Redis: keyset-пагинация,
оконные функции и распределённый rate limit ведут себя иначе на заглушках,
поэтому «зелёный» прогон на SQLite мало что значил бы.

## Развёртывание

```bash
make up              # весь стек
make migrate-docker  # миграции отдельным шагом
make logs            # журналы
make backup          # дамп сейчас
```

Порядок выкладки: миграции → API → фронтенд. Миграции добавляющие
( nullable-колонки, новые таблицы ) обратно совместимы, поэтому откат кода не
требует отката схемы.

Подробности — [docs/DEPLOYMENT.md](docs/DEPLOYMENT.md):
сертификаты, откат, обновление без простоя, резервное копирование.

## Переменные окружения

Все настройки читаются из окружения. Полный шаблон с пояснениями —
[`.env.example`](.env.example).

| Переменная | Назначение |
|---|---|
| `SECRET_KEY`, `JWT_SECRET_KEY` | Подпись сессий; ≥32 символа, обязательны в production |
| `DATABASE_URL` | `postgresql+psycopg://…` |
| `REDIS_URL` | Кэш, лимиты, очередь WebSocket |
| `TRUSTED_PROXY_COUNT` | Число прокси перед приложением; слишком мало — цикл редиректов, слишком много — подмена IP |
| `FORCE_HTTPS`, `SECURE_COOKIE` | В production обязательны `true` |
| `MODERATION_PROVIDER` | `local` · `openai` · `custom` |
| `MODERATION_FAIL_CLOSED` | `true` — при сбое классификатора всё уходит на проверку |
| `DATA_RETENTION_DAYS` | Срок хранения контента |
| `ADMIN_EMAIL`, `ADMIN_PASSWORD` | Первичный администратор |

Профиль `production` проверяется при старте: недостаточный `SECRET_KEY`,
отсутствие TLS или выключенная почта останавливают запуск, а не всплывают
через неделю.

```bash
make check-config    # эффективная конфигурация с замаскированными секретами
make secret          # сгенерировать стойкий секрет
```

## Решение проблем

**Публикация возвращает 419/403 про CSRF.** Токен читается из cookie при каждом
запросе. Проверьте, что `harmony_csrf` не заблокирована и `SameSite`
совпадает с `COOKIE_SAMESITE`.

**Бесконечный редирект на HTTPS.** `TRUSTED_PROXY_COUNT` не совпадает с
числом прокси. За nginx это 1; если TLS терминируется ещё и на балансировщике —
соответственно увеличьте.

**WebSocket не подключается.** Проверьте проброс `Upgrade`/`Connection` в
nginx и `SOCKETIO_MESSAGE_QUEUE`. Без очереди сокеты работают только внутри
одного пода.

**Письма не приходят.** `MAIL_BACKEND=console` печатает письмо в журнал — быстрый
способ проверить шаблон. В `smtp` проверьте `MAIL_SERVER`, порт и TLS-режим.

**Redis недоступен.** Приложение продолжает работать: кэш и распределённый
rate limit отключаются, логируется предупреждение. Это осознанный компромисс —
лучше временная деградация, чем отказ.

**Ошибка миграций на нескольких репликах.** Миграции запускаются отдельной
задачей (`make migrate-docker`), а не из контейнера API. Так реплики не
гоняются за одними и теми же DDL.

**Тесты падают на уникальном ограничении.** База переиспользуется между
тестами; фикстуры очищают таблицы. При ручном запуске вне pytest
убедитесь, что `APP_ENV=testing`.
