# Аутентификация

Как устроены регистрация, вход, сессии и восстановление доступа — и почему
каждое решение выбрано именно так.

---

## Модель угроз

| Угроза | Следствие для дизайна |
|---|---|
| Подбор пароля | bcrypt, ограничение частоты, блокировка |
| XSS крадёт токен | Токен в `HttpOnly`-cookie, а не в `localStorage` |
| CSRF | Отдельный токен с double submit |
| Утечка базы даёт вход | Токены хранятся хешами |
| Кража refresh-токена | Ротация, отзыв всех сессий при повторе |
| Перебор по списку почт | Одинаковые ответы и одинаковая работа |
| Захваченная сессия удаляет аккаунт | Step-up: пароль для критичных действий |
| Старый токен после блокировки | Проверка статуса на сервере |

---

## Регистрация

```
клиент                    сервис                    БД
  │  POST /auth/register    │                          │
  │  ──────────────────────▶│                          │
  │                         │ 1. schema               │
  │                         │ 2. оценка риска         │
  │                         │ 3. проверка занятости   │
  │                         │ 4. bcrypt(12 раундов)  │
  │                         │ 5. user.status=pending  │
  │                         │ 6. AuthToken (хеш)      │
  │                         │ 7. ConsentRecord        │
  │                         │ 8. письмо через Celery │
  │  201 { requires_email… }│                          │
```

Шаг 5: аккаунт создаётся неактивным. Без подтверждения почты вход
невозможен — иначе адрес можно было бы указать чужой.

Шаг 7: хеш принятого текста сохраняется рядом с записью о согласии. Позже
можно доказать, **какая именно** редакция документа была прочитана, даже
после того как файл изменится.

### Что не делается

- Нет поля «дата рождения», «пол» и подобных. Данные, которые никогда не
  используются, не собираются.
- Нет обязательного аватара. Пока нет, используется нейтральный цвет,
  назначаемый детерминированно.

## Подтверждение почты

Ссылка содержит 32-байтный токен со сроком 24 часа. В базе — **только
HMAC-SHA256**. Утечка дампа не даёт рабочих ссылок.

Токен одноразовый: `used_at` выставляется при использовании, повторный
запрос возвращает ошибку. Он привязан к назначению (`purpose`), поэтому
ссылка сброса не сработает как подтверждение и наоборот.

### Перечисление аккаунтов

`/auth/resend-verification` возвращает один и тот же ответ независимо от того,
существует адрес. Иначе этот эндпоинт стал бы инструментом проверки
зарегистрированности адресов — то есть фактическим сбором базы почт.

---

## Вход

```
POST /auth/login { identifier, password }
```

`identifier` — имя пользователя **или** почта.

| Неверный пароль | Неизвестный пользователь |
|---|---|
| `verify_password(...)` | `verify_password(...)` против фиктивного хеша |
| ответ 401 | ответ 401 |
| **одно сообщение** | **одно сообщение** |

Одинаковый текст и одинаковая работа. Иначе разница во времени или в
формулировке превращала бы эндпоинт в оракул.

После успеха:

- `failed_login_count` сбрасывается;
- выдаётся `access` + `refresh`;
- **крутится CSRF-токен** — значение, выданное до входа, больше не действительно;
- старые сессии обрезаются до 10 последних.

### Блокировка

Восемь неудач подряд → `locked_until` на 15 минут. Счётчик обнуляется при
блокировке, а не при успехе: иначе успешный вход «покупал» ещё попытки.

### Порядок проверок

Пароль проверяется **до** статуса аккаунта. Иначе заблокированный
пользователь, получающий 403, подтверждает, что его пароль верен.

## Сессии

### Токены

| Токен | Форма | Где хранится | Срок |
|---|---|---|---|
| access | JWT | `harmony_access`, HttpOnly | 12 ч |
| refresh | JWT | `harmony_refresh`, HttpOnly, path `/api/v1/auth` | 30 сут |
| CSRF | itsdangerous | `harmony_csrf`, **читаемая** | 1 ч |

Refresh ограничен по пути: он не уходит на каждый запрос к API, что
сокращает поверхность утечки.

### Claims

```json
{
  "sub": "42", "pid": "a1b2…", "username": "mira",
  "role": "member", "ver": "active",
  "email_verified": true,
  "iat": 1735689600, "exp": 1735732800, "jti": "…"
}
```

`ver` — статус аккаунта на момент выдачи. Он делает токен бесполезным после
санкции, **без списка отзыва**.

### Проверка на сервере

JWT сам по себе не отзывается, поэтому каждое обращение сверяется с БД:
роль, статус, `email_verified`. Заблокированный пользователь с действующим
токеном отклоняется.

Стоимость — одно чтение из кэша-строки по первичному ключу, а не запрос к
таблице пользователей. Индекс первичного ключа делает его дешёвым.

### Ротация

`/auth/refresh` выдаёт новую пару и отзывает старую.

Если отозванный refresh-токен предъявлен снова, это почти наверняка кража:
значит, у злоумышленника есть копия. В таком случае **отзываются все сессии
пользователя**. Пользователь обнаружит это как «меня выбросило» и сменит пароль,
что и требуется.

### CSRF

Двойная отправка: значение cookie повторяется в заголовке `X-CSRF-Token`.
Cookie намеренно читаемая — иначе клиент не сможет её отразить.

Проверка выполняется в `before_request`, до обработчика: новый изменяющий
маршрут защищён по умолчанию, а не по памяти разработчика.

Корректные `Origin` или `Referer` принимаются как эквивалент — иначе
не работали бы мобильные клиенты и `curl`.

`Authorization: Bearer` освобождён от CSRF: у него нет автоматического
присоединения браузером, поэтому вектора нет.

## Восстановление пароля

```
POST /auth/forgot-password { email }     → всегда одинаковый ответ
POST /auth/reset-password { token, password }
```

Токен живёт час и используется один раз. Смена пароля отзывает все сессии.

Ответ не различает существующий адрес и несуществующий: иначе эндпоинт
подтверждал бы наличие аккаунта.

---

## Смена пароля

Требует текущий пароль, даже когда пользователь уже вошёл. Сессионный токен
достаточен для чтения переписки, но недостаточен для смены учётных данных —
это ограничение ущерба при краже.

После смены отзываются все сессии, включая текущую. Пользователь входит
заново; это неудобство окупается тем, что украденный токен перестаёт
работать немедленно.

---

## Step-up для критичных действий

Удаление аккаунта, выгрузка данных, изменение ключевых настроек.

```
POST /auth/reauthenticate { password }  → { reauth_token, expires_in: 600 }
POST /me/deletion { reauth_token }      → 200
```

Токен одноразовый, живёт 10 минут и авторизует ровно одно действие.

Смысл: украденная сессия не позволяет уничтожить аккаунт. Пароль —
дополнительный фактор, который нельзя получить из cookie.

## Пароли

### Политика

| Правило | Обоснование |
|---|---|
| Минимум 10 символов | Длина важнее сложности |
| Минимум 2 типа символов | Отсекает «aaaaaaaa» |
| Блок-лист распространённых | Эффективнее, чем проверка «сложности» |
| Запрет 4 одинаковых подряд | Отсекает бессмысленные строки |

### Чего нет

Требования вида «одна заглавная, одна цифра, один символ» сознательно **не
применяются**: измерения показывают, что такие правила *снижают* энтропию,
потому что люди отвечают предсказуемыми заменами. Длина и разнообразие
работают лучше.

### Хранение

bcrypt, 12 раундов (≈250 мс). Соль уникальна на пользователя.

bcrypt игнорирует байты после 72-го. Пароли длиннее предварительно
хешируются SHA-256 — иначе суффикс перестал бы влиять на результат, и два
пароля с одинаковым началом совпали бы. Это покрыто тестом.

Повышение `BCRYPT_ROUNDS` пересчитывает хеш при следующем успешном входе:
пароль уже доказан, обновление бесплатно.
