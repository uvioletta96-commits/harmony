## Слои

```
┌──────────────────────────────────────────────────────────┐
│ api/        HTTP: маршруты, коды, контракт                │  знает про request
├──────────────────────────────────────────────────────────┤
│ services/   бизнес-логика, транзакции                    │  не знает про request
├──────────────────────────────────────────────────────────┤
├──────────────────────────────────────────────────────────┤
│ models/     SQLAlchemy, индексы, сериализация             │
├──────────────────────────────────────────────────────────┤
│ utils/      ответы, пагинация, логи, крипто, метрики      │
└──────────────────────────────────────────────────────────┘
```

Направление зависимостей — только вниз. Исключение: `api` регистрируется в
`app/__init__.py`, а `services` импортируют друг друга по необходимости
(`chat_service` → `user_service`), но никогда не наоборот.

**Почему так.** Бизнес-логика, не знающая про HTTP, тестируется без тестового
клиента: вызвал функцию, проверил состояние БД. Слой `api` остаётся тонким и
не содержит логики, которую пришлось бы дублировать при повторном
использовании.

## Поток запроса

```
1. nginx            TLS, статика, лимиты соединений, WebSocket upgrade
2. before_request   request_id, таймер, CSRF, глобальный rate limit
3. before_request   аутентификация (@auth_required) → g.current_user
4. view             валидация через Schema → services.*
5. services         бизнес-правила → models, security
6. after_request    security-заголовки, rate limit, логирование
7. teardown         откат при ошибке, возврат сессии в пул
8. error handler    единый конверт {ok, error}, без утечки деталей
```

Порядок имеет значение: CSRF проверяется **до** обработчика, поэтому новый
изменяющий эндпоинт защищён по умолчанию, а не по памяти разработчика.

## Модель данных

```
users ──┬── posts ──┬── post_media
        │           ├── reactions (UNIQUE user, post, type)
        │           └── comments ──┐ (self-FK parent, root)
        ├── comments               │
        ├── relationships (follow graph)
        ├── user_sessions          │
        ├── auth_tokens            │
        ├── privacy_settings       │
        └── conversations ──┬── conversation_members
                            └── messages

reports ─── moderation_actions      moderation_queue is the reports table
abuse_events / spam_signals         anti-spam scoring
notifications · audit_logs · consent_records · data_requests
```

### Решения, которые не видны в схеме

**`public_id` (128 бит) против `id` (счётчик).** Первичный ключ никогда не
покидает сервер. Перебор последовательных идентификаторов раскрывает объём
и упрощает эксплуатацию ошибок авторизации.

**`UTCDateTime` вместо `DateTime`.** PostgreSQL возвращает `timestamptz` как
aware-дата, SQLite — как naive. Смешивание даёт `TypeError` глубоко во
представлении, далеко от причины. Нормализация на уровне типа означает, что
весь остальной код может считать все даты aware и в UTC.

**Денормализованные счётчики.** `likes_count`, `comments_count`,
`posts_count` читаются при каждом рендере ленты. Пересчитываются из строк в
той же транзакции, а не инкрементом: повторный запрос или гонка не
расшатывают счётчик.

**Мягкое удаление постов и комментариев.** Строка сохраняется как
надгробие, чтобы обсуждения, история модерации и внешние ссылки разрешались
осмысленно, а решение можно было отменить.

**`PostMedia.post_id` допускает NULL.** Окно между загрузкой и прикреплением —
именно поэтому существует `owner_id`: без него один пользователь прикрепил бы
чужое изображение к своей публикации.

## Индексация и пагинация

### Keyset, а не offset

```sql
-- Индекс под точный запрос ленты
CREATE INDEX ix_posts_feed ON posts (status, created_at, id);

-- Курсор
WHERE status = 'published'
ORDER BY created_at DESC, id DESC
  AND (created_at, id) < (:last_created, :last_id)
LIMIT 15;
```

`OFFSET` пропускает и дублирует строки при вставке во время прокрутки.
Сравнение кортежей выражает лексикографический порядок одним предикатом и
оставляет индекс работоспособным.

### Почему `(created_at, id)`, а не только `created_at`

Даты повторяются. Без `id` в конце курсор не определяет строку однозначно, и
две записи с одинаковой секундой могут повторяться или теряться.

### Прочие индексы

| Таблица | Индекс | Запрос |
|---|---|---|
| `posts` | `(author_id, status, created_at, id)` | публикации пользователя |
| `comments` | `(post_id, created_at, id)` | обсуждение |
| `reactions` | `(user_id, created_at)`, unique `(user, post, type)` | лента лайков, защита от дублей |
| `conversations` | unique `direct_key` | один диалог на пару, без гонки «прочитал-создал» |
| `reports` | `(status, priority, created_at)` | очередь модерации |
| `abuse_events` | `(subject_type, subject_id, created_at)` | оценка риска |

### Комментарии: ранг по окну

```sql
row_number() OVER (ORDER BY likes_count DESC, created_at ASC, id ASC)
```

Ранжирование выполняется до пагинации. `OFFSET` здесь дал бы неверный
результат: новый комментарий с десятью лайками навсегда вытеснил бы старые с
первой страницы.

## Кэш и его инвалидация

Два правила, без которых кэш становится источником неверных данных:

1. **Кэшируется только неизменяемое или чётко ограниченное.** Ключ поста
   сбрасывается при каждой записи в этот пост; под ленту сбрасывается по
   тегу `feed`.
2. **Отказ открытый.** Любой сбой кэша деградирует в промах, а не в ошибку.

Ключи строятся как `harmony:<tag>:<blake2b(args)>`. Тег — первый аргумент, и
по нему можно сбросить целую категорию через `SCAN`, не угадывая хеши.

Отсутствие Redis добавляет таймер отказа: при недоступности следующая попытка
не раньше чем через 30 секунд. Иначе отказ Redis добавил бы секунду ожидания к
**каждому** запросу — деградация превратилась бы в отказ.

## Фоновые задачи

| Очередь | Задачи |
|---|---|
| `default` | общие |
| `notifications` | рассылка уведомлений |
| `email` | транзакционные письма |
| `moderation` | повторная проверка, истечение санкций, ротация риска |
| `maintenance` | сроки хранения, удаление, чистка, бэкапы |

### Настройки, которые важны

- `task_acks_late` + `task_reject_on_worker_lost` — задача подтверждается
  после выполнения. Без этого падение воркера молча теряет очередь.
- `worker_prefetch_multiplier = 1` — по одному заданию. Иначе воркер
  разбирает очередь себе в память и при смерти теряет всё невыполненное.
- `task_time_limit` — зависшая задача убивается, воркер выживает.
- `beat` — **один** экземпляр. Два планировщика означают двойные письма и
  двойные удаления.

Задачи `maintenance.*` реализуют политику хранения: посты старше
`DATA_RETENTION_DAYS` архивируются, невостребованные загрузки удаляются,
выгрузки GDPR стираются через 7 дней, истекающие ограничения снимаются.

## Realtime

**Аутентификация в `connect`, а не в каждом сообщении.** Неаутентифицированный
сокет не существует, и все последующие обработчики доверяют
`request.environ['harmony_user']`.

**Комнаты детерминированы:** `user:<id>` и `conversation:<id>`. Это позволяет
доставлять сообщение сокету, открытому на другом поде, при `SOCKETIO_MESSAGE_QUEUE`.

**Ограничение частоты — на сообщениях, а не на подключении.** Пользователь
законно переподключается на мобильной сети, но не отправляет 200 сообщений в
минуту.

**Клиент:** офлайн-очередь исходящих и повторное чтение истории при
переподключении — сообщение, написанное в метро, не теряется. Порядок
защищён сквозным номером, отбрасывающим дубликаты после переподключения.

## Конфигурация

`app/config.py`, 12-факторный стиль. Всё из окружения, типизировано, с
ранней валидацией.

Профиль `production` проверяется в конструкторе и **останавливает запуск** при:
коротком `SECRET_KEY`, не-PostgreSQL, выключенной почте, отсутствующем SMTP,
`SECURE_COOKIE=false`, отсутствии ключа внешнего модератора.

Мысль простая: неверная конфигурация должна обнаруживаться при развёртывании,
а не всплывать через неделю в виде необъяснимых ошибок.

`BaseConfig.normalise()` разрешает перекрёстные зависимости один раз:
`JWT_SECRET_KEY` берётся из `SECRET_KEY`, `SOCKETIO_MESSAGE_QUEUE` — из
`REDIS_URL`, и так далее.

## Обработка ошибок

Единый конверт на всё: успех и ошибка разбираются одним кодом на клиенте.

```json
{ "ok": false, "error": { "code", "message", "fields", "request_id" } }
```

`ApiError` — иерархия ожидаемых отказов; всё остальное превращается в 500 с
`request_id`, по которому находится строка в журнале. Детали исключения
попадают в ответ **только** в режиме отладки.

Сессия откатывается в `teardown_appcontext` при ошибке: иначе отравленная
сессия уйдёт в пул и сломется позже, в другом месте.

## Наблюдаемость

`request_id` из заголовка `X-Request-ID` проходит через nginx, попадает в лог
и в заголовок ответа — одна строка связывает сообщение пользователя с записью.

Логи структурированы, одно событие на строку. Маскирование секретов
выполняется форматтером, а не разбросанными проверками. Стабильное поле
`action` предназначено для алертинга.

Метрики помечаются **шаблоном маршрута**, а не сырым путём: иначе
кардинальность взорвалась бы перебором идентификаторов.

## Как добавить эндпоинт

1. Бизнес-логика — в `services/`, без `request`.
2. Валидация входа — `Schema` в том же сервисе или в представлении.
3. Маршрут — в соответствующем `api/blueprint.py`.
4. Декоратор авторизации: `@auth_required`, `@auth_optional` или
   `@moderator_required`.
5. Ошибки — готовыми классами из `utils/responses.py`, с `code` для клиента.
6. Документация — путь в `spec/openapi.yaml`, затем `make openapi`.
7. Тест — в `tests/`, с проверкой границы авторизации, а не только успеха.

CSRF и глобальный rate limit уже действуют: новый изменяющий маршрут защищён
автоматически.

---

## Как добавить модель

1. Класс в `app/models/`, наследующий `PrimaryKeyMixin`, `PublicIdMixin`,
   `TimestampMixin`.
2. `UTCDateTime` вместо `DateTime` — иначе вернётся неоднородность дат.
3. Индекс под **точный** запрос, а не «на всякий случай».
4. Импорт в `app/models/__init__.py` — иначе таблица не создастся.
5. `flask db migrate -m "…"` и `flask db upgrade`.
6. При необходимости — инвалидация кэша в сервисе после записи.
