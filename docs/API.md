# OpenAPI

Исходник спецификации API — `spec/openapi.yaml`. Из него генерируется
`backend/app/static/openapi.json`, который отдаётся по адресу
`/api/openapi.json` и открывает интерактивную документацию `/api/docs`.

## Зачем два файла

YAML — источник истины: его читают люди, на нём проще обсуждать изменения в
review. JSON — то, что грузит браузер. Держать рукописный JSON значит
гарантированно получить расхождение с реальными маршрутами.

## Рабочий цикл

```bash
# после правки spec/openapi.yaml
make openapi          # перегенерировать JSON

make openapi-check    # в CI: упадёт, если JSON устарел
```

## Проверка соответствия маршрутам

```bash
python tools/check_routes.py
```

Скрипт сравнивает таблицу маршрутов Flask со списком путей спецификации в
**обе стороны**: неописанный эндпоинт валит проверку (документация не может
незаметно отстать от кода), и описанная операция без маршрута — тоже (контракт
обещает то, чего сервер не делает). Имена параметров пути при сравнении
стираются: Flask регистрирует `/posts/<post_id>`, спецификация пишет
`/posts/{post_id}`, и это один и тот же маршрут.

## Идемпотентность там, где клиент может повторить запрос

| Операция | Поведение | Почему |
|---|---|---|
| `POST /posts/{id}/reactions` `type=like` | ставит лайк, повтор ничего не меняет | клиент, не получивший ответ, повторяет запрос — иначе он случайно снимет лайк |
| `type=unlike` | снимает лайк, повтор ничего не меняет | симметрично |
| `type=toggle` | переключает | для кнопки-сердечка, где клик означает «противоположное текущему» |
| `POST /auth/refresh` | ротация refresh-токена | повтор со старым токеном обнаруживается как перехват и завершает все сессии |
| `POST /me/deletion` | требует одноразовый `reauth_token` | повтор получает `403 reauth_invalid`, а не создаёт вторую заявку |

## Ошибки аутентификации различают *почему*

| Ситуация | Код | Почему не `401` |
|---|---|---|
| Токена нет или он невалиден | `401 token_invalid` | клиенту нужно войти заново |
| Сессия отозвана (выход, смена пароля) | `401 session_revoked` | то же самое |
| Аккаунт заблокирован модератором | `403 account_banned` | токен подлинный, и предлагать «войдите снова» — тупик: войти нельзя |
| Аккаунт приостановлен | `403 account_suspended` | то же |
| Аккаунт ожидает удаления | `403 account_deletion_pending` | доступны только `/me/deletion` и `/me/deletion/cancel` |

Порядок проверок важен: сначала состояние аккаунта, затем живость сессии. Иначе
санкция маскировалась бы общим «сессия завершена», и пользователь не понял бы,
что с ним происходит.

## Удаление поста обратимо

`DELETE /posts/{id}` — мягкое удаление: строка остаётся со статусом `removed`
и скрыта от всех, включая автора. Текст сохраняется, иначе `POST
/posts/{id}/restore` было бы обещанием, которое нельзя выполнить. Настоящее
стирание происходит при удалении аккаунта (`purge_account`), и только там.

## Что документировано

- Все ответы в общем конверте `{ok, data, meta}` / `{ok, error}`
- Схема аутентификации: cookie, bearer, CSRF
- Курсорная пагинация и заголовки rate limit
- Полный перечень кодов ошибок с объяснением, почему тот или иной код важен
- Примеры для неочевидных случаев (409 при дубликате, 202 при проверке)
- Ограничения: минимальная длина поиска, глубина комментариев, число картинок

## Соглашения

| Аспект | Решение |
|---|---|
| Версия | В URL (`/api/v1`), не в заголовке |
| Идентификаторы | `public_id` (32 hex), не `id` |
| Даты | ISO-8601 UTC, `2026-01-31T12:00:00Z` |
| Время ответа | `HH:MM:SS.sssZ` |
| Отсутствующее поле | `null`, не пропуск |
| Обязательность | Явно перечислена в `required` |
| Ошибка | Всегда `{code, message}`, поле `fields` — для форм |

## Версионирование

Путь версионируется, поэтому изменение контракта — новая версия:

- `v1` — обратно совместимые добавления полей и маршрутов
- `v2` — удаление поля, изменение типа, изменение кода ошибки

Клиенты, написанные против `v1`, продолжают работать, пока `v1` жив.
